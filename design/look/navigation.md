# Navigation

A topic of [Look](../look.md): the router, going back by the bar's button, by the edge swipe and by Android's back.

- **A router of our own, the route as state** (`src/lib/router.svelte.ts`): `Route` is a union tagged by `name` (`no-machines`, `home`, `agent` with its `machine` and `pane`, `terminal` with its `machine` and the agent's row, `machines`, `machine` with its `id` and `adding`, `start` with its `machine`, from an agent the `workspace` to choose, and, from an issue, the `issue` it starts on (`StartingIssue`: its project when it is a repository's, the places it can start in, the workspace Start was opened with, the issue and the prompt cornercase will use), `changes` with its `machine`, `workspace` and `title`, `change` with its `machine`, `workspace` and `path`, `files` with its `machine`, `workspace` and `title`, `file` with its `machine`, `workspace` and `path`, `issues` with its `machine`, and `issue` with its `machine`, the `project` it was listed with, whether it is a repository's (`repository`), `key` and `source`), kept in a `$state` stack with `go`, `settle`, `setBase` and `back`, which never pops the first route. `settle` leaves the base and one route over it: the agent the start screen started is all that stays over the board, so `Back` goes to the board and not to a form already sent, nor to the issue and the list the form came from, and its `agent` route carries `starting` (`design/starting-work.md` › After it starts). It is not 015's `settle`, rejected below, which replaced the whole stack when the base changed. `Router.latest(name)` gives the topmost route of a name anywhere in the stack, so the issues and an issue keep their state while a screen opened from them is on top (Starting work › From an issue). That first route, the base, follows from the connection's state (`routeFor`): with no machine at all it is `no-machines`, otherwise `home`, which shows the board. A row of the board pushes `agent` with `go`, the agent's `Terminal` pushes `terminal` over it, its `Changes` pushes `changes` and a file of the list pushes `change` over that (`design/changes-and-files.md` › The screens), its `Files` pushes `files` and a file of the tree, or a diff's `Whole file`, pushes `file` (Changes and files › Files), and each `Back` pops one. `Router.reviewed` and `Router.browsed` give the workspace of the last `changes` or `change`, and `files` or `file`, above the chat, not only on top, so the changes stay alive under a `file` opened from a diff. `changes`, `change`, `files` and `file` keep their machine for the same reason as `agent`, since workspace ids are each server's own too. The route keeps the machine it was opened on, since pane ids are each server's own: the connection bar also opens Machines over an agent, whose `Chat` lives on beneath it (`Router.opened`), and after switching machines there, `Back` comes back to that `agent`, whose `Chat` (made for the route's machine, `chatOf`) then shows it as gone rather than finding the new machine's agent with the same id (`design/chat.md` › The screen). A `terminal` keeps its machine for the same reason, and `terminal_open` opens its tab on the active machine: `openedTerminal` gives it only while that machine is still the active one, and otherwise `App` shows the gone agent in its place, with the connection bar, rather than opening that tab id on the new machine. The terminal's screen has no connection bar, so nothing opens Machines over it today; the rule covers any later way of switching under it. Rejected: dropping the `agent` routes from the stack on a switch, a second rule for what stays above the base besides `setBase`'s.
- **The connection sets only the base** (`setBase`): `App.svelte` calls it on each `connection-changed` and `agents-changed`, and what was pushed above the base stays. So the agent's screen and its terminal stay while the rows keep changing under them, every half second while an agent works, and Machines and a machine's screen stay open too, also when the active machine is removed (`connection-changed` to `none`) while others remain. A base of the same name leaves the stack alone. `no-machines` empties it, since nothing above it has a machine to show, so a terminal never outlives the last machine. A hot reload, which mounts `App` again, starts from the base. Rejected: replacing the top route on every change, as 014 did, which took the agent's screen back to the board and closed Machines at the next change; and 015's `settle`, which replaced the whole stack when the base changed, and so closed Machines once the first machine was added from it.
- **Ways in and back**: the connection bar's last control is a 44 px button with the `server` icon that pushes `machines` (P1). Rejected: tapping the bar's text, which does not look like a button, and a button on `home`, which belongs to the agents board. The board's `Start`, at its top right, pushes `start`, and rests while the connection is not `connected`, since nothing could be sent; an agent's `New agent` pushes it with the agent's workspace, and rests the same. Start's `Issue` pushes `issues`, a row pushes `issue` and the issue's `Start` pushes `start` with it. A row's `Edit` pushes `machine`; `Scan again` pushes it with `adding`, which opens its form for the code at once. Each of these screens goes back by its bar's back button or by the edge swipe (below). Deleting a machine pops back to Machines, then sets the base from the machines left. Android's back button calls the same `goBack` (below).
- **The back button** is `chevron-left` and the title of the route below the top (`titleOf(router.below, …)` in `src/lib/navigation.ts`, pure: `Agents` for `home`, `Machines`, the changes' and the files' title, the agent's label (from the active machine's rows, with them, so a flow's member is its role as in its chat, and a subagent's chat goes back to `‹ orchestrator`), a machine's name, `Start`, a file's name, of a diff or of the tree, `Issues` and an issue's key), in `--accent` at 17 px, as Mail's `‹ Inboxes`. Its `aria-label` is `Back to <title>`, or `Back` when the title is unknown (an agent no longer among the rows). The label is measured and hidden, the chevron alone left, when it does not fit its column beside the 44 px of the chevron (`fitsLabel`): an agent's titles are long, so over the terminal and the changes the chevron is often alone. The `aria-label` stays whole. Hidden is `visibility: hidden` out of the flow, so it is still measured as the room changes.
  - **`--accent` and not `--brand`**, which the ticket named: `#005fff` on `--veil` and `--glass` is about 3.8:1, enough for an icon (3:1) but not for 17 px text (AA asks 4.5:1). `--accent` is what the chevrons and the chat's bar already used.
- **In two panes the side settles** (062, Wide windows › The side and the detail): the board's rows, its `Start` and the bar's `Machines` replace the detail with `settle` (`side` in `App`), and what the detail opens is pushed as here; in one pane all of them push. An agent straight over the board has no back button there (`NavBar`'s `rooted`).
- **One `goBack`** in `App.svelte` for the chevron and the swipe: it pops the top route, and closes the diff first when the top is a `change`, as `leaveDiff` did, and the file when it is a `file`, listing the tree again after, as 026's `leaveFile` did, so the two ways back cannot differ.
- **The edge swipe** (iOS only): a finger that starts within 20 px of the screen's left edge and moves right drags the screen with it, and lifted far enough it goes back. `BackSwipe` (`src/lib/backSwipe.ts`) is pure, with the clock passed in, like `swipe.ts` and `pinch.ts`; `watchBackSwipe` turns the touches into its calls, installed by one `$effect` in `App` only while `backSwipes` holds (iOS and a route below the top: never on the board or `no-machines`; never in two panes, its third argument, since the detail's left edge is not the screen's, [Wide windows](wide.md) › The side and the detail). Each new touch is ignored while `html.scanning` shows the camera.
  - **The thresholds**, close to UIKit's and to the terminal's 10 px tap (021): the swipe is claimed once the finger has moved 10 px, if each of its moves went more than twice as far right as up or down (`LEAN`, below), and dropped at the first move that did not; lifted past 35 % of the width, or moving right at 0.5 px/ms or more, it goes back, else the screen settles. It is dropped when a second finger comes, on `touchcancel` or `pointercancel`, and when the finger stays more than 300 ms before it is claimed, which leaves a long press and text selection alone. A still tap at the edge stays a tap: the terminal's first column and the first key of the rows of keys still take it.
  - **Touch events, not pointer events**: only `preventDefault` on a `touchmove` that is not passive stops the terminal's native `pan-x` and the sideways scroll of the diff and the code blocks; once the browser pans, pointer events get only a `pointercancel`. The listeners are in capture on `document`, and `preventDefault` comes from the first move at the edge that goes more than twice as far right as up or down (`holds`, `LEAN`, about 27° from the horizontal), while the swipe waits, and from every move once it is claimed: WebKit starts its pan within those first 10 px, and a `preventDefault` after it no longer stops it (Checked, below). A move from the edge up, down or left, and every touch off the edge, scroll the page as before.
  - **Its cost**: WebKit decides on the first `touchmove` whether the touch scrolls, so a drag held from its first move does not scroll the page at all, even when the swipe drops it at the claim. Twice as far rather than the claim's own rule (more right than up or down), so that a scroll up or down that starts at the edge with a tremor to the right still scrolls (review of 2026-11-10); so a drag from the edge between about 27° and 45° from the horizontal never goes back. The swipe drops a touch at the first move it did not hold, since WebKit may have started its pan there, and that pan's `pointercancel` would drop it anyway: before, such a drag was still claimed at 10 px if more right than up or down, and so went back from the chat and Changes but, in the simulator, only 1 time in 3 from the diff, whose sideways scroll took the touch (review of 2026-11-10). Dropping it everywhere makes the gesture the same on every screen. Rejected: a lower `LEAN` (about 1.5, 34°), which narrows that band but lets more scrolls with a tremor be held.
  - **The shared edge** (`src/lib/edge.svelte.ts`, `idle`, `pending` or `claimed`), which the watcher writes and the terminal's grid reads: while the swipe waits or holds the finger, the grid ignores its moves (no lines to the PTY, no scrolling, no pinch), and a lift once claimed cancels the tap, so the keyboard does not open. Rejected: cutting the pointers with `stopPropagation` in capture, which would leave their ids hanging in the terminal's `Swipe` and `Pinch`. A touch that starts off the edge reaches everything as before: the pinch, `pan-x`, the swipe of 021 and the tap in the terminal, the sideways scroll of the diff and the code blocks, and the chat's scrolling and selection.
  - **`translateX` only during the swipe**: on `.page`, a wrapper of the screen without the connection bar and the toasts, and in the terminal on its fixed `.screen` (`shift`), since a transform on an ancestor turns its `position: fixed` children relative to it: the connection bar would jump on a scrolled page, and the terminal's screen would move with the page. At rest there is no transform at all. While it slides, `.sliding` paints `--glass` and a shadow along its left edge, over the app's ground and wash. `#app` clips sideways (`overflow-x: clip`, not `hidden`, which would make it a scroll container and unstick the bar), so the shifted screen never widens the page on iOS 16 and later. Safari 15 has no `clip`, so there the page widens while the finger drags, harmless since the moves are held; `Router.below`'s `Array.prototype.at`, like the `findLast` before it, already asks for iOS 15.4.
  - **Lifting**: back slides the screen out to the full width over `--leave` (120 ms, ease-out) and calls `goBack` once it is out; settling slides it back over the same time. The finger's own moves are not eased (`Shift`'s `eased`). Touches are ignored while it leaves: new ones, and the moves, lifts and cancels of another finger, which would bring the screen back before `goBack` takes it away. With Reduce Motion the screen does not move: past the threshold it goes back at once, and short of it nothing happens.
- **Android** (`src/lib/platform.ts`, `platformOf`: `Android` in `navigator.userAgent`, case aside, and iOS for everything else, empty or unknown included, since iOS is the app that ships): the same bar with `arrow-left`, no title below and the title on the left (`auto 1fr auto`), and no edge swipe, since both edges are the system's back gesture there. Rejected: `platform()` of `@tauri-apps/plugin-os`, a crate and a package for one bit.
- **Android's back** (`src/lib/backButton.ts`, 032), its button and its gesture alike: over a route below the top it calls `goBack`, as the arrow does, one step each; while the scanner shows it cancels the scan (`OpenScanner` in `src/lib/scanner.svelte.ts` holds the scanner that scans, which `App` cannot reach otherwise, until its scan ends, so it keeps no scanner whose field is gone, and `stop()` ends it as its Cancel does, with no error), and the form stays; on the base (`home`, `no-machines`) it is the system's, which leaves the app (the task's P3, a). Nothing goes to the PTY: the back is no key. `backPressed` decides, pure and on iOS always `none`; `watchBackButton` listens with `onBackButtonPress` of `@tauri-apps/api`, installed by one `$effect` in `App` only while the press is the app's (`handled`), so on the base no listener exists and Tauri's own handler lets the system have it (with a listener it only fires the event; without one it goes back in the WebView's history, which the app never writes, or to the system). The `$effect` depends on that one boolean, so moving between two routes above the base keeps the same listener, and what to do is read at the press, never when it was installed. Registering is asynchronous: a press in the instant a route appears or goes may still find the old state, harmless; a listener registered after the effect ended is removed at once; a refusal is a toast. Rejected: `exit` on the base, which drops the streams abruptly where Android users expect the system's back; a listener always installed that hands the base's press to the system, for which `@tauri-apps/api` 2.12 has no call.
  - **Its limits**: with the keyboard open, the first back is the keyboard's, which closes it, and the second the app's, as everywhere on Android. The system's predictive back animation never shows over a route above the base, since Tauri's callback holds the press. Leaving from the base ends the activity, as before 032, so the next start connects again; staying in the background instead (`moveTaskToBack`) would be a change of `MainActivity.kt`, not made.
  - **Checked on 2026-11-10** in an Android emulator (arm64, Android 17, API 37, a debug APK, Tauri 2.12.5, against a cornercase 0.13.19 of its own) with `input keyevent KEYCODE_BACK`: from the chat to the board, the terminal to the chat, the changes to the chat, a diff to the changes, the files to the chat and a file to the files, one step each; from the board the app left. In the terminal with GBoard open, the first back closed it and the second went to the chat, and the pane (a `cat -v`) got no byte from any of them. The scanner opened from the form to add a machine closed on a back with no error, and the next back went to the board, since the form is Machines' own state and not a route. Not checked live: `no-machines` and the scanner over it (the same rule as `home`, in the tests), and a real phone's gesture.
- **Checked on 2026-11-10** in the iPhone Air simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5), the app built with `tauri ios build --debug`, against a bridge of its own on `127.0.0.1` and cornercase 0.13.19 with a stand-in agent, the touches made by XCUITest (`press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:)` from x = 2) and the screen read by `simctl` while the finger was held:
  - The back button and the swipe went back from the agent to the board, from the terminal to the agent, from a diff to the changes, from the changes to the agent and from a machine to Machines; the label read the screen below (`Agents`, `claude`, `main`, `Machines`). Held halfway, the screen followed the finger with the shadow on its left and the ground behind, and the connection bar stayed put. A drag of 100 pt held and lifted settled back; one of 300 pt went back; a quick one of 70 pt went back by its speed.
  - Found: with `preventDefault` only once claimed, a drag from the edge of a zoomed terminal scrolled its grid sideways and never moved the screen, since WebKit had started the pan before the 10 px of the claim. Holding the page from the first move right fixed it: the zoomed and the fitted terminal slid, and the grid's and the diff's sideways scroll were where they had been once the screen settled.
  - Off the edge, the terminal's pinch, its sideways scroll, its swipe through the history and its tap that opens the keyboard went on as before; at the edge, a still tap opened the keyboard and a drag up scrolled the grid.
  - With the keyboard open, on the terminal or on the chat's field, the screen slid under the fixed keyboard, and the screen it went back to took the whole height once the keyboard closed.
  - After the review's fixes (same setup, 2026-11-10): the bar of Machines, the changes and a diff rests at 76 pt, right under the clock, and stays there while a long diff scrolls under its veil; the changes' totals end 16 pt from the edge, as the rows do; a drag from the edge that goes mostly down scrolled the diff; and the swipe still went back from a diff, the changes, the terminal and the chat, a short one in the terminal settling.
  - To check on an iPhone: the feel of the thresholds with a real finger, a drag up or down from the edge of a long chat with a tremor to the right, and whether a natural back swipe ever starts steeper than `LEAN` (checked only straight, on the terminal's grid), and Reduce Motion, unseen live.
- **Rejected for the swipe**:
  - Mounting the route below so that it shows while the screen slides: `App` mounts only the top route, and mounting the one below would start its streams (the terminal's `surface`, `changes list --follow`, the chat's reads); it would be cheap only for the board. The ground and the shadow show instead.
  - WKWebView's `allowsBackForwardNavigationGestures`: wry 0.57.1 has `with_back_forward_navigation_gestures`, but Tauri 2.12.5 does not expose it; it walks WebKit's back-forward list, of loads and `pushState`, while the router is state with no history; it shows an old snapshot of the screen before, not the live one; and it could not tell itself from the terminal's sideways scroll.
- Rejected: `svelte-spa-router` 5.1.1 and any URL or hash routing. A WebView has no address bar, so URLs give the user nothing, and they would bring a dependency and strings to parse; a union lets `pnpm check` check a route's parameters, such as the pane of 016's chat. `design/architecture.md` already chose routing as state over SvelteKit.
