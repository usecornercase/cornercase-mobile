# Chat

The agent's screen a row of the board opens (`src/routes/agent/Agent.svelte`, Board › A row): its header, which stays at the top (The screen), a thread of the conversation as the phone saw it, your sends and the agent's messages as markdown, kept on the phone (Kept on the phone), and a live line of what the agent does (The thread), and a composer to answer it (`src/routes/agent/Composer.svelte`): a rounded capsule with the field for text (Answering) and an icon that opens a row of keys over it to answer with a key (Keys). Its state lives in `src/lib/chat.svelte.ts` (`Chat`), without markup, so vitest tests it; the commands come in by injection, as in `addMachine.svelte.ts`. The thread's rules are pure functions in `src/lib/thread.ts`, with `now` as an argument, as `board.ts` does, and the conversation's in `src/lib/history.ts`. The capsule's `+` attaches images from the phone's photos, which wait on the phone and reach the agent's input with the next send (Attaching an image).

Topics, in `design/chat/`:

- [Reading the message](chat/reading.md) (`crates/core/src/cli/last_message.rs`, `src/lib/chat.svelte.ts`): what `read --last-message` gives, one-shot beside the queue, a message that cannot be read, when it is read again, one read at a time.
- [Answering](chat/answering.md) (`src/routes/agent/Composer.svelte`, `src/lib/chat.svelte.ts`): the capsule and its field, a send through the queue, what comes back on your bubble, `--timeout 30`, a false `not confirmed`, why `waiting` takes no text.
- [The thread](chat/thread.md) (`src/routes/agent/Thread.svelte`, `Sent.svelte`, `AgentLine.svelte`, `src/lib/thread.ts`): what it holds and the gap line, your bubble, the live line and its no news, one live region, a message that grows, where the thread lands.
- [Keys](chat/keys.md) (`src/routes/agent/KeyRow.svelte`, `src/lib/keys.ts`, `crates/core/src/cli/keys.rs`, `src-tauri/src/commands/chat.rs`): the row behind an icon, which keys and how they go, `Ctrl-C` asking for a second tap, `Esc`, the light tap, a key behind a held send.
- [The question](chat/question.md) (`src/routes/agent/Question.svelte`, `QuestionCard.svelte`, `src/lib/question.svelte.ts`, `crates/core/src/terminal/asking.rs`, `question.rs`, `question/card.rs`): the question read from the screen by a passive `surface`, the crop, the options, the fallback and the card, the composer's height, opening and closing it.
- [Attaching an image](chat/attaching.md) (`src-tauri/plugins/photos`, `src-tauri/src/commands/chat/attach.rs`, `src-tauri/src/state/attached.rs`, `src/lib/attach.svelte.ts`, `src/routes/agent/Thumbnails.svelte`): the button and the picker, the images shrunk on the phone, kept until `Send` and bounded, sending and a paste that fails, the thumbnails.
- [Kept on the phone](chat/history.md) (`crates/core/src/history.rs`, `history/store.rs`, `src-tauri/src/commands/history.rs`, `src/lib/history.ts`): where the conversation is kept, one `boot` per machine, its entries and caps, writes, failures, `History`, forgetting a machine.
- [Seen from the phone](chat/seen.md) (`crates/core/src/cli/mark.rs`, `src-tauri/src/commands/chat.rs`, `src/App.svelte`): opening a `done` agent marks it reviewed, only `done`, where it is watched, a failure, no `--boot`, the fitted terminal.

## Markdown

- **A tree, never HTML**: `src/lib/markdown.ts` parses the text with `mdast-util-from-markdown` and GFM (Architecture › Dependencies) and keeps a closed tree of its own: paragraphs, headings, emphasis, strong, strikethrough, inline code, code blocks, lists (with their checkboxes), quotes, GFM tables, breaks and rules. `Markdown.svelte` and `MarkdownNode.svelte` draw it with Svelte's own elements, so nothing goes through `{@html}`, which `svelte/no-at-html-tags` refuses and no comment may silence.
- **Headings one level down**: `#` is an `h2`, `##` an `h3`, and so on up to `h6`, since the agent's title is the `h1` of its screen (Look › Components) and VoiceOver walks a screen by its headings. They all look the same (`.heading`), so only the outline changes.
- **A link to the web opens in the system's browser** (2026-11-15): a link whose address is `http` or `https` with a host (`opensOut`, `src/lib/links.ts`), written as `[words](url)`, `<url>`, a bare URL or a `www.` address (GFM), is drawn as an `<a>` in `--accent`, underlined, and a tap hands its address to Tauri's opener plugin (`openUrl`), which opens Safari or the phone's browser; the click's own navigation is cancelled, so the WebView never leaves the app, and `-webkit-touch-callout: none` keeps iOS from offering its preview, whose Open would load the page in the app. Any other link (`javascript:`, `mailto:`, `file:`, a reference link) stays its words. Why: the agents' answers often point at a pull request, a doc or an issue, and copying the address by hand on the phone was the only way. Rejected: a Rust command of our own around the opener, where the plugin's own scope (`capabilities/default.json`, `https://*` and `http://*` only) already limits what the WebView may open, as the haptics and the scanner do.
- **What is not drawn as itself**: raw HTML stays as its text, any other link as its words, an image as its `alt`, and a node the tree does not know as its text. The CSP already blocks images from elsewhere, but no `<img>` is drawn either.
- **Code blocks and tables scroll sideways** inside their own container, the code in `--font-mono`, so the screen itself never does. The text is parsed in the WebView at each read and not virtualised: a message of tens of KB is accepted as it is.

- **The composer stays at the bottom** (`position: sticky`) on glass, so it can be reached while a long message scrolls. Its height is capped (`--over-composer`), so a question, the keys and a grown field scroll inside it rather than covering the bar. With the keyboard closed it pads the safe area at the bottom; with the keyboard open it drops that padding, since the keyboard covers the home indicator (041).
- **With the keyboard open the screen is what is left visible** (041, `src/routes/agent/Agent.svelte`): while anything covers the screen (`covered` of the terminal's `Keyboard`, Terminal › Typing › The height with the keyboard), the chat's section leaves the page and becomes a fixed column at `visualViewport.offsetTop`, as tall as `visualViewport.height`: the bar on top, the thread in the middle, which scrolls within itself (`Thread`'s `boxed`), and the composer at its foot, whose cap takes that height (`--seen`) instead of the screen's. The header turns compact at once and the large header leaves the eye (`.spoken`, so its `h1` stays for VoiceOver), which leaves the thread the room; the subagents line stays. The thread goes to its end as the keyboard opens, and as it closes only if it was at its end: a reader who had scrolled up keeps the same distance from the end once the page scrolls again (`keepFromEnd`, which the box's own scroll records), so dragging the keyboard away from the middle of the thread never jumps to the bottom; and when its box changes height while open (the keys opening, the field growing) only if it was at its end, which its own scroll records (`atEnd`), so your bubble and the last message sit right above the capsule, and reading higher up is never taken away (The thread › A message that grows): going to the end at every change, as the terminal's grid does, took the place of a user who had scrolled up to reread something with each line the field grew (041's review). The connection bar moves with it (Connection › The connection bar). Why: iOS lays the keyboard over the page without shrinking it and lifts the page so the focused field shows, and the field sat at the page's bottom (`position: sticky`), so with a short thread the lift (396 pt on a 390 × 844 phone) took the connection bar, the header and the bubble above the screen, leaving the capsule alone over a blank page, and the user did not see the bubble of what they had just sent (041's review). Rejected: undoing the lift with `window.scrollTo`, which iOS may do again at each caret move; the page sized to the visible height but left in its flow, which iOS still lifts; the whole section as the scroller with its sticky bar and composer, which depends on how WebKit counts a scroller's padding for `sticky`; and the chat always in a fixed box, which loses the tap on the status bar that scrolls to the top. Limits: while the keyboard is open, a swipe back draws the column `env(safe-area-inset-top)` lower for the length of the swipe, as the page's `transform` becomes its containing block; and opening the keys drew iOS' caret, for a moment, over the row of keys, until the next key typed (Checked live).
- **The keyboard follows the finger down**, as in WhatsApp or Messages: short scrolls of the thread leave it open, and a drag that reaches the keys takes them down with the finger, and lets them go back up if the finger turns. That is UIKit's interactive dismissal (`keyboardDismissMode = .interactive`), which the `keyboard` plugin turns on in every scroll view of the WKWebView each time the keys show, since WebKit backs each box that scrolls, the thread's among them, with a `UIScrollView` of its own, made when the box first scrolls (Architecture › Plugins of our own › `keyboard`). Once the keys are gone the plugin blurs the focused field, so a tap on it opens them again. All of it holds only in the chat, which marks the document while it is open (`followKeys`, `data-keyboard="follows"`) and which the plugin asks each time the keys show: the chat alone moves with the keys, and elsewhere (the terminal, the forms) a drag would leave a gap between the column and the falling keys (review of 2026-11-15; rejected: the whole app). While the finger takes the keys down, WebKit leaves `visualViewport` as it was until they are gone, so the chat's column kept its height and the composer floated above the falling keys (seen on the iPhone on 2026-11-15): the plugin tells the page where the keys begin on every frame of the drag (a `keyboardtop` event, from UIKit's `keyboardLayoutGuide`, which follows the finger), and the composer and the thread's messages move down together by how far below what the page sees the keys now begin (`dropped`, `src/lib/keyboardTop.svelte.ts`), each with a `transform`, so nothing is laid out again while the finger drags: the last message rides above the composer and older ones come in at the top, as in WhatsApp. Once the keys leave their place the thread stops scrolling, as WhatsApp's does: from then on the finger moves only the keys, and the thread grows at its foot and shows older messages at its top; before that, scrolling and the keys moving under the same finger moved the messages twice. The plugin pins the scroll view being dragged (`ScrollLock`) while the keys are lower than where they last showed, and lets it go when they come back up or go. While the composer rides down its field's caret is hidden (`.leaving`, `caret-color: transparent`): iOS draws the caret itself over the page, where the editor last put it, and a `transform` does not move it, so it stayed in the middle of the screen. The keys' line reaches the page a frame or two late (the plugin's event crosses to the web process), so with a quick finger the composer trails above the keys; a ground of the composer's colour hangs under it down past the screen's foot (`.floor` in `Agent`, moved by the same `transform`), so what shows in that moment is the composer's ground, not a gap. For the messages to have somewhere to go, the thread's box reaches behind the composer and the keys while the keyboard is open (`margin-bottom: -100vh`, which its `flex: 1` takes back, so the composer stays where it was), and ends with as much room (`.room`, `100vh` less the gap), so its end still sits right above the composer and its scroll, `atEnd` and `fromEnd` read as before; the composer's ground is opaque, so nothing shows through it. Rejected, after trying them on the iPhone the same day: stretching the column to the keys' line, which laid the thread out again on every frame while the finger dragged it, and, at its end, sent it to its end on every frame, so the screen shook; and moving only the composer, which left an empty band between the messages and it. The plugin tells `null` once the keys have shown, and keeps its last line when they go until the page sees them gone, so the composer does not jump back up in between. Rejected: closing the keyboard from JavaScript once a finger went down 12 px (tried first, on 2026-11-15), which closed it on every short scroll up and could not move the keys with the finger, since the page cannot reach them.
- **No bar over the keyboard**: WKWebView puts its form bar (‹ › and ✓) over the keys of every field, and the chat has one field, with Send in the capsule, so the bar only took 44 pt of the thread. The `keyboard` plugin takes it away on iOS (Architecture › Plugins of our own › `keyboard`).
- **One `Chat` per opened pane of a machine**, which `App` makes when the route opens it and drops on `Back` (`src/App.svelte`). It lives on under the agent's terminal, under its workspace's changes and a diff over them, and under Machines (and a machine) opened from the connection bar over it (`Router.opened` in `src/lib/router.svelte.ts` is `chatOf` of the highest `agent` or `terminal` of the stack, skipping `machines`, `machine`, `changes` and `change`; `chatOf` is the machine and pane of `agent` and of `terminal`'s row, and `App` makes a new `Chat` only when one of the two changes), so coming back keeps the text typed and the message read, and it goes on hearing its events meanwhile. Rejected: a new `Chat` on coming back, which lost the text typed and read the message again; and, for Machines, dropping the `Chat` while it shows, the same loss on a `Back` that changed nothing. Under Machines, switching to another machine or removing the active one leaves the `Chat` gone by the rules below (another machine, or none), and so does a tap on the active machine's own row, which connects it again and turns its rows `null`: accepted, a new connection that may be a restart, rather than a second rule telling a reconnection to the same server from one to a new server. `App` gives it the active machine with the rows of each `agents-changed`, and the `pane-status-changed` events that match its machine and pane (`touches`). A failed key or image reaches `App` as its reason, for the toast; a failed send stays in its bubble.
- **The thread outlives the `Chat`**: your live bubble stays under the terminal and under Machines, and its `Chat` goes on `Back` to the board and when the agent is gone; a send still on its way then writes nothing and shows no toast, so it comes back `Not confirmed` (The thread › Only the last send is live). Reopening the agent from the board shows its conversation again, kept on the phone by machine, `boot` and pane (Kept on the phone), with no send live. This reverses 036's "reopening the agent from the board starts clean" and its "rejected for now: keeping the bubble by machine and pane outside the `Chat`": on 2026-11-10 the user asked for the chat to read as a conversation, which a thread that starts clean on each visit cannot be. The images waiting are still kept only while the `Chat` lives (Attaching an image).
- **A `Chat` belongs to the machine its route was opened on**, since pane ids are each server's own (Look › Navigation): once the active machine is another one, or none, it is gone for good, even if the new machine lists a pane with its id, so it never reads or sends to that pane on the new machine. This is the check `openedAgent` made before the chat (027), moved into `Chat.see`, which already decides when the agent is gone; rejected: keeping `openedAgent` beside it, two places deciding the same thing.

## Gone

- **The agent is gone** when a list of rows lacks its pane (the pane was closed, or the agent quit and left its shell), or when the rows turn `null` after the screen had seen its row (a restart, a new `Store`), or when the active machine is not the one it was opened on (The screen). Then it says `This agent is no longer running.` under the bar and its back button, the field goes, and the text typed is lost; the conversation stays on the phone (Kept on the phone).
- **For good**: a later list with the same pane does not bring it back. After a restart the server may give that id to another agent, and the screen must neither show that agent's text nor send it what was typed for the first one (Upstream gaps › `--boot`).
- **Before the first list** (`null` without having seen the row: connecting, a new `Store`) the screen does not know yet and shows the board's mark (Board › A row).
- **An agent the phone is closing** is not counted as gone while its `Closing…` lasts: `Chat.see` keeps the last row, and the app returns to the board when the close ends (Board › Closing an agent).
- **An agent the app just started** has no row yet: `Chat.see` takes `starting` from its route, and until the row comes a list without the pane does not count it as gone, while the screen says `Starting <agent>…` (Starting work › After it starts). Once the row was seen, or on another machine, the rules above hold.

## Left out
